# Each Guest picks its fastest reliable Channel, with a fallback

We do not force one **Channel** everywhere. macOS and Linux **Guests** use SSH (multiplexed, ~tens of ms per command, native stdout). Windows **Guests** on VMware Fusion use `vmrun runProgramInGuest -interactive`, with a unique output file per call, and fall back to SSH plus an interactive Scheduled Task.

The reason Windows differs: an SSH session on Windows cannot touch the logged-in user's desktop, so UI automation over SSH needs a Scheduled Task hop, while `vmrun -interactive` reaches the desktop directly and is proven in practice. On providers without such a native exec (Hyper-V, UTM, Parallels without tools), SSH plus Scheduled Task becomes primary. `vmlab doctor --bench` measures both Channels so defaults can be revisited with data.

**Verified on Tart (macOS 26 Guest, Tart 2.37, guest agent 0.14).** `tart exec` runs in the logged-in GUI (Aqua) session but has no TCC grants of its own: its first Apple Event to System Events opens a consent dialog nobody can click, and the call hangs. Once provisioning writes TCC grants for the agent binary, `tart exec` drives System Events like SSH does. It stays the fallback, not the primary, because it is slower: a no-op takes about 60 ms over `tart exec` and about 14 ms over multiplexed SSH. Provisioning grants both Channels, so a fallback also carries UI calls. The grants name the agent by path, so upgrading the agent inside a Base guest means re-provisioning it.

**Verified on Fusion (Ubuntu 26.04 arm64 Guest, Fusion 26, open-vm-tools 13).** SSH stays primary: about 12 ms per call, against about 3 s over vmrun, which needs five vmrun invocations per command (copy the script in, run it, copy stdout, stderr and the exit code out) because `runProgramInGuest` returns no output. vmrun remains the fallback for when the Guest's network or sshd is down. Its commands run as the Guest user outside any login session, so the call's script sets the environment an SSH login has (HOME, PATH, XDG_RUNTIME_DIR, the session bus). vmrun takes the Guest password only on its command line, so the password is visible in the Host's process list while a vmrun call runs. We accept this: the password is random, stored with mode 0600 in vmlab's home, used by nothing but vmrun (sudo in the Guest is passwordless), and guards a throwaway Guest on Fusion's private NAT network. Spec story 11's "never in process lists" holds inside the Guest, where the hand-written labs leaked it; this exception covers the Host side of the vmrun Channel only.

**Verified on Fusion (Windows 11 25H2 arm64 Guest, Fusion 26).** Both Windows Channels deliver the same thing: a script that runs the command in the logged-in user's desktop session, unelevated, and writes its exit code and raw output to one result file (`guest/windows/call.ps1`). A Channel only carries that script in and the result out, so a fallback never changes what a command sees. SSH is primary at about 1.4 s per call (scp the script in, one ssh command registers an interactive Scheduled Task, runs it and waits for the result), vmrun `runProgramInGuest -interactive` the fallback at about 3 s (four vmrun invocations per call). vmrun needs neither the Guest's network nor sshd, and it is the only Channel before provisioning installs sshd, which is what the wizard uses. Both need the user logged in: an SSH session cannot reach the desktop at all, and vmrun refuses `-interactive` until someone is signed in.

What Windows Guests cost us, each found the hard way:

- vmrun runs programs as the Guest user with a **filtered token** (Medium integrity), interactive or not, so nothing it starts can administer Windows. Only a person can answer Windows' consent prompt: it is drawn on the secure desktop, where `vmcli MKS sendKeyEvent` does not reach (it types nothing anywhere, in fact). So `vmlab base create windows-11` asks for one click on it and then, elevated, lets administrators elevate without a prompt in this throwaway Guest.
- **Windows' sshd stops reading a command's stdin at about 4 KB** and the call hangs for good. Nothing rides on stdin over SSH: the call's script, its stdin and Build artifacts all travel as files over scp (`Channel.send_file`), which also keeps the command line short — sshd runs commands through `cmd.exe`, whose 8191-character limit hangs rather than fails.
- A Scheduled Task's PowerShell **cannot read a script from `C:\Windows\Temp`**: that folder grants every user write but no read, and the task dies with 0xFFFD0000 and no output. Call files live in `C:\ProgramData\vmlab\calls`.
- .NET puts a **UTF-8 BOM in front of a command's stdin** once the Guest's code page is UTF-8, which is what provisioning sets. The runner asks for a BOM-less console input encoding, but only when the call has stdin: doing it unconditionally hangs in a Scheduled Task's console.

Fallback happens only when a Channel reports that it could not carry the call (cannot connect, session lost, helper missing). A command that exits non-zero is a result, not a Channel failure. A call that times out is killed and fails the Run without falling back, because the command may already have run in the Guest and repeating it over another Channel could run it twice. A Channel that hangs on every call therefore shows up as a timeout, and `vmlab doctor` names it.

## Considered options

- **SSH everywhere** — one quoting model and provider-independent, but the Windows desktop is only reachable through an extra hop.
- **Provider-native exec everywhere** — `vmrun` loses stdout and costs seconds per call; `tart exec` works with TCC grants but is about 4× slower than multiplexed SSH.
