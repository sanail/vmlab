# Each Guest picks its fastest reliable Channel, with a fallback

We do not force one **Channel** everywhere. macOS and Linux **Guests** use SSH (multiplexed, ~tens of ms per command, native stdout). Windows **Guests** on VMware Fusion use SSH to vmlab's call server in the desktop session, and fall back to `vmrun runProgramInGuest -interactive`, with a unique output file per call.

The reason Windows differs: an SSH session on Windows cannot touch the logged-in user's desktop, so calls over SSH go to vmlab's call server, which runs there, while `vmrun -interactive` reaches the desktop directly. We first expected vmrun to be primary; measured, the SSH hop is faster (see below). On providers without such a native exec (Hyper-V, UTM, Parallels without tools), SSH to the call server is the only Channel. `vmlab doctor --bench` measures every Channel so defaults can be revisited with data.

**Verified on Tart (macOS 26 Guest, Tart 2.37, guest agent 0.14).** `tart exec` runs in the logged-in GUI (Aqua) session but has no TCC grants of its own: its first Apple Event to System Events opens a consent dialog nobody can click, and the call hangs. Once provisioning writes TCC grants for the agent binary, `tart exec` drives System Events like SSH does. It stays the fallback, not the primary, because it is slower: a no-op takes about 60 ms over `tart exec` and about 14 ms over multiplexed SSH. Provisioning grants both Channels, so a fallback also carries UI calls. The grants name the agent by path, so upgrading the agent inside a Base guest means re-provisioning it.

**Verified on Fusion (Ubuntu 26.04 arm64 Guest, Fusion 26, open-vm-tools 13).** SSH stays primary: about 12 ms per call, against about 3 s over vmrun, which needs five vmrun invocations per command (copy the script in, run it, copy stdout, stderr and the exit code out) because `runProgramInGuest` returns no output. vmrun remains the fallback for when the Guest's network or sshd is down. Its commands run as the Guest user outside any login session, so the call's script sets the environment an SSH login has (HOME, PATH, XDG_RUNTIME_DIR, the session bus). vmrun takes the Guest password only on its command line, so the password is visible in the Host's process list while a vmrun call runs. We accept this: the password is random, stored with mode 0600 in vmlab's home, used by nothing but vmrun (sudo in the Guest is passwordless), and guards a throwaway Guest on Fusion's private NAT network. Spec story 11's "never in process lists" holds inside the Guest, where the hand-written labs leaked it; this exception covers the Host side of the vmrun Channel only.

**Verified on Fusion (Windows 11 25H2 arm64 Guest, Fusion 26).** Both Windows Channels run a command the same way: in the logged-in user's desktop session, unelevated, in the user's profile folder, killed with what it started a second after its timeout, its exit code and raw output returned as one JSON result. vmrun `runProgramInGuest -interactive` carries a script that does this (`guest/windows/call.ps1`) in and its result file out: four vmrun invocations, about 3 s per call. SSH is primary at about 40 ms per call (0.25 s for a PowerShell command, PowerShell's own start): vmlab's call server (`guest/windows/call-server.ps1`, C# the Guest compiles when it has no copy for this version, in about 0.5 s; a Base guest provisioned by this vmlab has one in its snapshot, since provisioning's own calls start it) listens on 127.0.0.1 in the desktop session, and each call is a connection forwarded to it with `ssh -W` over the multiplexed connection, so nothing starts in the Guest but the command. An interactive Scheduled Task starts the call server at the first call after a boot or restore (about 2 s, more while Windows is still signing the user in); the call server's version, a hash of its script, picks its port, so a newer vmlab never talks to an older call server. It listens on 127.0.0.1 only and asks for nothing, so any program in the Guest, of any account, could have it run a command as the Guest user. We accept this as we accept the password on vmrun's command line: the Guest is a throwaway on Fusion's private NAT network, and provisioning already lets that user elevate without a prompt. Before the call server (2026-09-24) every SSH call registered a Scheduled Task of its own and started PowerShell twice: about 1.4 s per call even with PowerShell compiled to native code, and a one-call Run took 13 s against 2 s on macOS and Linux; it now takes about 4 s, 2 of them the call itself. vmrun needs neither the Guest's network nor sshd, and it is the only Channel before provisioning installs sshd, which is what the wizard uses. Both need the user logged in: an SSH session cannot reach the desktop at all, and vmrun refuses `-interactive` until someone is signed in.

What Windows Guests cost us, each found the hard way:

- vmrun runs programs as the Guest user with a **filtered token** (Medium integrity), interactive or not, so nothing it starts can administer Windows. Only a person can answer Windows' consent prompt: it is drawn on the secure desktop, where `vmcli MKS sendKeyEvent` does not reach (it types nothing anywhere, in fact). So `vmlab base create windows-11` asks for one click on it and then, elevated, lets administrators elevate without a prompt in this throwaway Guest.
- **Windows' sshd stops reading a command's stdin at about 4 KB** and the call hangs for good. Nothing rides on a command's stdin over SSH: a call and its stdin travel over the connection forwarded to the call server, which carries any size, and Build artifacts as files over scp (`Channel.send_file`), which also keeps command lines short — sshd runs commands through `cmd.exe`, whose 8191-character limit hangs rather than fails.
- Windows' sshd refused a second session on one connection ("Session open refused by peer"), so SSH sessions (starting the call server, scp) connect on their own; forwarded connections share the master connection.
- **.NET Framework sockets are inheritable**: an app a call launched would hold the call's connection open, and the Host would wait for the app to quit. The call server makes its sockets non-inheritable.
- A connection to a Windows port nobody listens on is refused only after about 2 s. The Host tries the call server first only when it may be running; after vmlab stopped or restored the Guest it starts the call server straight away.
- A Scheduled Task's PowerShell **cannot read a script from `C:\Windows\Temp`**: that folder grants every user write but no read, and the task dies with 0xFFFD0000 and no output. Call files and the call server's script live in `C:\ProgramData\vmlab\calls`.
- .NET puts a **UTF-8 BOM in front of a command's stdin** once the Guest's code page is UTF-8, which is what provisioning sets. call.ps1 asks for a BOM-less console input encoding, but only when the call has stdin: doing it unconditionally once hung in a Scheduled Task's console. The call server sets it once, in its own headless console.

**Confirmed by `vmlab doctor --bench`** (2026-09-23, Apple Silicon Host, 20 no-op calls per Channel after one warm-up, medians): macOS 26 on Tart, SSH 15 ms against `tart exec` 38 ms; Ubuntu 26.04 on Fusion, SSH 9 ms against vmrun 2.9 s; Windows 11 on Fusion, SSH 1.5 s against vmrun 2.5 s. The preferred Channel is the fastest on every Guest, so the defaults stand. With the call server (2026-09-24, a Scenario's own timing, medians) a Windows no-op over SSH takes 40-50 ms, a PowerShell one about 0.2 s and a UI call about 0.4 s, alone or with a macOS and a Linux Lab running beside it (`--parallel`). Bench says so per Lab, and names a faster fallback when a Host measures otherwise.

Fallback happens only when a Channel reports that it could not carry the call (cannot connect, session lost, helper missing). A command that exits non-zero is a result, not a Channel failure. A call that times out is killed and fails the Run without falling back, because the command may already have run in the Guest and repeating it over another Channel could run it twice. A Channel that hangs on every call therefore shows up as a timeout, and `vmlab doctor` names it.

## Considered options

- **SSH everywhere** — one quoting model and provider-independent, but the Windows desktop is only reachable through an extra hop.
- **Provider-native exec everywhere** — `vmrun` loses stdout and costs seconds per call; `tart exec` works with TCC grants but is about 4× slower than multiplexed SSH.
